# Metadata Operations — Hydration, Classification & Repairs

Deep operational reference for the media metadata pipeline. Relocated from `AGENTS.md`.
Summaries: `docs/MULTI_PROVIDER_METADATA.md`, `docs/DOCUMENTATION.md` §10 (Metadata System) and §19 (TVDB Integration).
Read this file BEFORE touching anything under `apps/api/src/media-metadata/**`, hydration crons, or Metadata Health repairs.

## Non-negotiable invariants

- Preserve user watch data, ratings, reactions, votes, and comments during every repair or remap.
- Treat authoritative external IDs as stronger evidence than titles; never guess when provider evidence is ambiguous.
- Keep provider/type namespaces separate. A wrong-type match creates or repairs the correct entity; it never merges incompatible structures.
- Mobile never calls metadata providers directly; provider access remains behind the API.
- Repair operations must be idempotent, rate-limit aware, and safe to retry.

## TMDB hydration (one call per entity)

- TMDB hydration is ONE call per entity: `TmdbProvider.getShow/getMovie` use `append_to_response` (external_ids, credits, watch/providers, videos, **keywords, translations, reviews, recommendations**, + up to 12 `season/N` appends for shows — TMDB caps appends at 20; longer shows fall back to per-season calls for the tail). Before full show hydration, `getShowRoutingProfile` performs one lightweight identity/genres/keywords/external-ids request with no season details. General automatic anime classification requires both TMDB Animation genre (16) and the `anime` keyword; neither signal alone is sufficient. The only routing exception is the TV Time dead-series replacement guard documented below under canonical structure. Old rows with `keywords = null` get one light `/keywords` lookup; provider failure leaves classification pending rather than persisting a false GENERAL result.
- **Aired-season tail-skip (interactive detail views only):** `ensureShowFull(..., { skipAiredSeasons: true })` — passed ONLY from `ShowsService.getShow` — builds `airedSeasonSkipper` and passes it to both `getShow` calls: the per-season tail fetch (seasons beyond the 13 appended) is SKIPPED for seasons stored complete: number ≠ 0 (specials churn), stored `episodeCount` == the provider summary `episode_count` (any structural change refetches), every active episode has an airDate, and the latest aired > 7 days ago (post-air correction buffer). Skipped seasons are filtered out of the normalized payload before `persistShow`, so owner-aware `syncSeasons` never touches their rows — `airedCount`, texts, and locale overrides are preserved. Background paths (metadata backfill, repairs like `forceEnglishRehydrate`, TMDB changes sync, imports, Auto Hydrations) call `ensureShowFull` WITHOUT the flag and always fetch full structure — their goal is correctness. First hydrations never skip.
- **Locale parking (`metadata_provenance.localeUnavailable`):** every request-locale fetch goes through `maybeApplyLocaleOverrides`. When the base payload's translations map provably LACKS the locale (exact app-locale key, then 2-letter base — TMDB keys are ISO 639-1), the fetch is skipped and the locale is stamped; a parked locale is not re-requested for 7 days (`isLocaleFetchParked`), and `ShowsService.getShow`'s `localeMissing` re-trigger ignores parked locales. This kills the infinite loop where a show re-fetched the provider's English fallback on EVERY open in a language the provider doesn't have. `TvdbProvider.getShow` now also exposes the full app-locale `translations` map (from the meta=translations block) — used for the same detection and for bulk-storing TVDB locale overrides in `persistShow`.

## Multi-network shows

- Multi-network shows: `shows.network` stays ONE string column, but hydration joins up to 2 network names with `·` (`NETWORK_SEPARATOR`) — TMDB from `networks[]`, TVDB from `companies[]` filtered to Network type (`companyTypeId = 1`, studios skipped) with `originalNetwork` fallback. Shared helpers in `packages/shared/src/media.ts`: `formatNetworks` (storage) / `firstNetwork` (display). Episode details render the full joined string; compact surfaces (watch-next/upcoming cards, Android widgets via `widgets/data.ts`, iOS widgets via a Swift-side split) show the first network only.

## TVDB v4 artwork types

- TVDB v4 artwork types: SERIES 1=banner (WIDE), 2=poster, 3=background; MOVIE 14=poster, 15=background. The mapper takes poster=2/backdrop=3 (series) and poster=14/backdrop=15 (movies) — a banner only ever fills the BACKDROP as a last resort, NEVER the poster. Legacy rows are cured by Metadata Health `bannerAsPoster` + `POST /admin/repair-banner-posters/run`: URL-only duplication is normalized locally; true bad artwork is force-refreshed with `ARTWORK_ONLY` from the persisted show owner (TMDB or TVDB). Movies prefer their correct-kind TMDB identity and fall back to TVDB only when no TMDB identity exists. Structure is never rewritten by artwork repair.

## Light upserts & English base

- Light upserts are born with an English base: the TMDB side fetches `fetchEnBase` (one light call), the TVDB side `fetchEnBaseTvdb` (`TvdbProvider.localizedShowBase/localizedMovieBase` — one translations call, no episodes/artworks). Base = English, request language goes to the override slots, `title_locale='en'` — but ONLY when the provider actually has an English title (otherwise the localized base stays with an honest `title_locale=lang`). This is what stops the nonEnglishContent/nonEnglishBase stats from re-growing from live non-en traffic.

## Canonical show structure

- General shows with both verified series ids are re-compared every 30 days by the structure-reconcile candidate job; imports may enqueue the same deduplicated authority evaluation sooner when their official TVDB footprint or episode identities cannot fit the active graph.
- `Show.structureProvider` is the only season/episode and show-metadata authority. Movies remain TMDB-owned. Strict TMDB Animation+`anime` shows remain TVDB-owned, and a previously unknown TVDB series is born `ANIME_TVDB` when TVDB explicitly returns its `Anime` genre (`id=27`, name/slug `anime`). The create-only gate is shared by search, import, and identity promotion; it stamps classification/authority immediately when the genre is already present and otherwise queues one bounded TVDB inspection/full-hydration job. It never changes an existing catalog row inline. For every other show with a verified TMDB↔TVDB series identity, the authority job fetches both complete graphs and compares all regular S/E coordinates against TVDB **official** order, including announced future episodes: equivalent graphs receive `GENERAL_TMDB`; any divergence receives `GENERAL_TVDB`, whose metadata and structure are both hydrated from TVDB official order. A TMDB-only show remains `GENERAL_TMDB`; an unresolved TVDB-only show remains the locked `TVDB_ONLY_FALLBACK`. Provider failure is `unknown`, not equivalence: existing ownership stays unchanged and new provisional rows use rule version 0 so Metadata Health retries. Ordinary reads keep the persisted owner sticky; only Metadata Health, scheduled structure jobs, or an import-queued evaluation may change it. IMDb identifies titles but never owns structure. The guarded dead-ID import recovery remains stricter: after exact local catalog matching misses, an exactly-one TVDB replacement must also match the imported structural footprint before it receives `ANIME_TVDB`. Every provider season must appear in the archive and contain the highest watched episode; an exact title/alias may have additional unwatched episodes, while a weaker descriptive-prefix match still requires exact per-season episode counts. A bounded pre-colon legacy-title retry handles descriptive suffixes. The 24-hour freshness gate controls when the owner refreshes and cannot change ownership. `persistShow` blocks non-owner structural writes; cast-only TVDB refreshes update cast without touching metadata freshness or episodes.
- Import replacement verification hydrates a bounded TVDB search candidate without episode structure first, so localized translations can establish identity and an incompatible season range can be rejected before downloading a large franchise episode graph. Only title/year/Anime candidates with the exact imported regular-season range receive the full footprint check and `ANIME_TVDB` hydrate. Explicit dead legacy `OVA(S)`/`Special(s)` collection identities may reuse exactly one TVDB Anime series whose translated title equals the suffix-free base even without watched coordinates. If no live TVDB series can represent a deleted anime OVA but TMDB exposes a uniquely alternative-titled show with the imported footprint, normal TMDB ownership is retained; the importer never invents a TVDB series mapping.
- Authority migrations run only through `StructureRemapService`: compare and preview first, hydrate the target provider with `STRUCTURE_REMAP` under the shared media lock, transfer user data, then stamp the new owner. The complete target season graph is staged in one database transaction; canonical episode-id collisions roll that graph back instead of leaving provider-less partial rows. Exact target-provider identities reuse and reactivate their existing `LEGACY_UNMAPPED` episode rows, preserving internal episode ids and attached user data. An explicit evaluation stages the selected complete snapshot even when the provider owner is unchanged, so local rows converge when the provider adds, removes, or renumbers episodes; an unexpectedly empty selected graph is deferred. Equivalent TMDB/TVDB official regular graphs remain TMDB-owned and take the no-remap path: the complete TMDB snapshot is refreshed, then exact-coordinate TVDB episode aliases are attached. A pre-existing legacy special can therefore no longer veto alias attachment for hundreds of otherwise equivalent regular episodes. The gate is all-or-nothing for regular-episode visibility: if any stale regular episode carrying meaningful user data has no proven target, the migration aborts before structural writes instead of switching authority and quarantining that history out of active queries. Provider-only S0 rows are outside the regular-structure comparison; shared specials are matched from the losing provider's verified complete snapshot, while unmatched S0 rows with user data remain `ACTIVE` as non-authoritative supplements and do not veto a proven regular-TV owner change. An ID-less `LEGACY_UNMAPPED` special may correlate to one canonical S0 row only when exact date, S0 coordinate, normalized title, and runtime tolerance all agree. Protected stale rows claim canonical targets before data-free staging duplicates, allowing a retry to remove harmless partial-run debris without hiding real history. Matching uses exact episode external ids first, then verified provider dates, aired absolute order, S/E coordinates, and bounded date/runtime evidence; regular titles are supporting evidence only and specials remain stricter. Two provider episodes converging onto one canonical episode merge watched state, unique ratings/reactions/character votes, history, comments, and external reviews. One combined episode splitting into two official parts marks both watched, copies history/ratings/reactions/character votes to both, and physically clones the current comment/reply tree onto the second part; the two social threads evolve independently afterwards. A matcher-version bump reconsiders earlier legacy rows once.
- TVDB structural snapshots are fail-closed and complete: pagination follows `next` beyond the old 12-page boundary, waits through the shared internal throttle, and rejects on incomplete pagination or provider failure. Reconciliation does not transfer, quarantine, or stamp a show when foreign-episode verification fails. Entirely default, unwatched `user_episode_status` placeholders do not by themselves retain an otherwise data-free stale episode; watched state/history, ratings, reactions, votes, comments, and external reviews remain protected.
- Episode S/E coordinates are indexed rather than globally unique so a locked remap can stage the canonical row beside a provider-foreign row before transferring data. A successful strict authority migration leaves only the canonical active **regular** graph; ambiguous regular user-data mappings block the owner change, unmatched data-free rows may be deleted, and protected provider-only S0 supplements remain active without participating in progress, watch-next, or future contamination selectors.
- Progress eligibility is provider-neutral: active regular episodes with a null or past/present `airDate` count, while only episodes explicitly dated in the future are excluded. This keeps undated TVDB official episodes in season/show totals. Import, onboarding, structure-remap, and interactive hydration rebuild `user_show_status` with the same rule.
- TVmaze may enrich a canonical episode with a precise airtime/airstamp only for seasons whose complete S/E coordinate set exactly matches the active canonical provider graph. Split/combined structures are skipped season-by-season and any stale coordinate-derived `airTime` is cleared; TVmaze must never overwrite canonical provider dates by coordinate alone. Structure Remap tolerates a bounded UTC/local-day rollover for verified provider dates, while still requiring one unique canonical target and runtime proof before two split parts may reuse one combined episode.

### Canonical-structure rollout

1. Apply the additive schema migration, but do not start repair yet.
2. Deploy structural-write enforcement to every API and worker instance.
3. Run report and dry-run batches; review authority reasons, missing provider ids, mappings, and legacy projections.
4. Enable `STRUCTURE_REPAIR_ENABLED=true` only after that review. The DB-managed job processes a bounded `STRUCTURE_REPAIR_BATCH_SIZE` batch (default 200, maximum 1000), resumes from its last successful cursor, and reports its next cursor and remaining backlog; run it daily (existing DB schedules must be edited explicitly) until the candidate set reaches zero.
5. Keep the compatibility read from `metadataProvenance.structureProvider` during rollout. Remove it only after the typed-owner metric remains at zero across refresh/import/backfill traffic.

Migration application and production repair are separate operator-approved actions. Repair retries are idempotent and every title is serialized by the media write lock. For one broken title, use Metadata Health's targeted Structure Reconcile action with its current internal media id: run Dry Run first, then Repair only when the preview reports zero protected rows needing review. A nonexistent/stale media id is returned explicitly as `not-found` and counts as a failed target instead of looking like a successful no-op.

## Kitsu/Jikan enrichment

- Kitsu and Jikan may supply alternative titles, typed external IDs, subtype, dates, and artwork. Their matches, Japanese origin, studios, and non-genre TVDB type signals remain supporting evidence only. The direct TVDB classification signal is its explicit `Anime` genre on the create-only path above. Cast-purpose TVDB refreshes use `CAST_ONLY`, skip the episode-list request, and never write seasons. They persist the bounded top-40 display cast plus every staged import character id found in the complete TVDB extended-series response; this makes rank-41+ TV Time votes resolvable without making every ordinary hydration store an unbounded cast.

## Cross-type contamination (MOVIE row carrying show data or vice versa)

- Cross-type contamination (a MOVIE row carrying a `shows` row or vice versa, e.g. a TVDB series id attached to a TMDB movie row): prevented by kind-aware `findMediaByExternal(provider, value, kind)` (TMDB/TVDB ids live in separate movie/series namespaces) + type guards in `persistShow`/`persistMovie` (wrong-type existing → create a new row, never merge). Cured by `MetadataBackfillService.repairTypeMismatches` (Metadata Health `structuralTypeMismatch` stat + `POST /admin/repair-type-mismatch/run`): detach stray-kind external id → recreate the correct entity → `StructureRemapService.remapEpisodesToMedia` transfers watch data → stray structure deleted only after an explicit check that NO stray episode still carries user data (status/rating/reaction/vote/comment — guards the empty-target partial-fetch case) → own-provider rehydration restores base metadata.

## TVDB-id conflicts (multiple TVDB ids of the same kind on one row)

- TVDB-id conflicts (a row carrying MORE THAN ONE TVDB id of the same kind): benign TVDB-merge leftovers vs id poisoning from the removed title-attach behavior. `POST /admin/repair-tvdb-id-conflicts/run?mode=dry-run|repair` verifies show IDs through TMDB `/find` and movie IDs through TVDB's own remote TMDB/IMDb IDs. The row's kind-scoped TMDB ID is the primary anchor and IMDb is the movie fallback anchor. Only resolved aliases that contradict that anchor are detached; unresolved aliases remain untouched, aliases resolving to the same identity are kept, and unanchored/mixed rows are reported as ambiguous. Repair stamps a fingerprinted `metadataProvenance.tvdbIdAudit`: unchanged benign sets leave the actionable count permanently, unresolved sets retry after 90 days, and ambiguous sets retry after 180 days. The raw alias-set count remains informational. Detaching an external id never deletes user data.
- Wrong-kind aliases (a MOVIE provider id attached to a SHOW row or SERIES id attached to a MOVIE row) are counted separately from structural type mismatches. `POST /admin/repair-wrong-kind-external-ids/run?mode=dry-run|repair` detaches them only when the row has at least one correct-kind TMDB/IMDb/TVDB anchor. Unanchored rows remain ambiguous for manual review. All hydration, rating, recommendations, artwork, and import selectors use the media row's expected provider kind so a wrong-kind alias cannot route future writes.
- Movies missing TMDB identity (API metric remains `providerDuplicateMovies` for compatibility): TVDB/IMDb MOVIE rows with no TMDB ID are candidates, not guaranteed duplicates. `POST /admin/repair-provider-duplicates/run?mode=dry-run|repair&count=N` resolves IMDb first, then TVDB `/movies/{id}/extended` remote TMDB/IMDb IDs, then an exactly-one title+year TMDB search, then conservative local metadata. TMDB's unsupported TVDB-movie `/find` path is never used. A verified TMDB ID with a local row merges under one transaction; without a local row it attaches to the existing row and hydrates from TMDB. The merge preserves movie status, watch history, watchlist/favorite/custom-list membership, ratings, reactions, movie comments and attachments, external reviews, external IDs, and watch-provider alerts (collisions retain newer configuration and active intent). Ambiguous matches are skipped; definitive no-match rows are parked for 180 days only in repair mode. Dry-run performs all provider resolution but writes nothing and returns per-row evidence.
- Prevention is centralized in `lightUpsertMovieTvdb`, which is shared by discovery, import title fallback, direct TVDB-ID import recovery, and promotion. It uses TVDB remote IDs to reuse or create the TMDB canonical movie, attaches both IMDb and TVDB aliases, and repoints a verified alias away from a historically poisoned owner without deleting that owner's user data. `ensureMovieFullTvdb` routes bridgeable movies to normal TMDB hydration; only true TVDB-only movies persist TVDB metadata.

## Non-English base/content repairs

- Non-English base titles (rows whose base/override was written in the wrong language — old contamination that makes English users see foreign titles): Metadata Health `nonEnglishBase` stat (rows explicitly marked `title_locale != 'en'` — rows with an UNSET marker are NOT counted since most have a fine English base) + `POST /admin/repair-non-english-base/run` (`repairNonEnglishBase`) + the daily `english_base_repair` cron (1000 rows/run, default `0 13 * * *`): clears `metadataRefreshedAt` and re-runs the standard hydration (TMDB id first, TVDB fallback) — `persistShow/persistMovie` rewrite the English base and overwrite the wrong value in the `en` slot. User data untouched. The `title_locale` marker is rewritten on EVERY persist to describe the base just written (`enData ? 'en' : lang`; TMDB hydrations always persist an English base → 'en') — it is NEVER inherited from the previous row value (a stale-marker inheritance once made repaired rows keep their non-en marker, so the stat never dropped). Rows marked 'en'/unset with wrong-language CONTENT (the marker lies — the marker stat can't see them) are handled by the `nonEnglishContent` suspect stat + `POST /admin/repair-english-content/run?count&deep` (`repairNonEnglishContent`) + the nightly `english_content_verify` cron (2000 rows/run): suspects = the English-visible title (`titles.en` → base) contains non-ASCII; EVERY candidate is verified against the provider's canonical English title (one light `localizedShowBase/localizedMovieBase` call, TVDB `getShow/getMovie('en')` fallback) and only real mismatches are re-hydrated via the shared `forceEnglishRehydrate` (comparison is case/quote/space-insensitive). Suspects are taken most-popular-first (what users see gets fixed first). CONVERGENCE: a verified-as-English row is remembered in `metadata_provenance.enContentVerifiedTitle` and leaves the suspect pool/stat until its visible title changes (new contamination re-arms it) — legit non-ASCII titles (Pokémon) are verified ONCE, so repeated runs and the stat both drain (the stat still fluctuates: live non-en traffic/imports keep creating new light-upsert stubs that enter the pool immediately). `deep=1` verifies every unverified row with external ids (catches pure-ASCII foreign titles), paging with the wrapping Redis cursor `EN_CONTENT_DEEP_CURSOR`. `forceEnglishRehydrate` also marks `user_stats_summary.stale = true` for every user with watch history on the fixed row — stats snapshots (marathons/genres/networks) bake titles in and are otherwise invalidated ONLY by watch/import events, so without this a successful repair stayed invisible on profile pages. Repair failures (unverifiable rows, provider errors) are WARN-logged for the first 10 per run (prod runs at info level). A provider RATE LIMIT stops the batch early (same as the sibling backfills) instead of failure-stamping every remaining row. A row whose provider simply has NO English overview is treated as overview-verified — a rehydrate cannot fix what the provider lacks, and mismatching it would fail → park → retry forever. BIRTH-STAMP: `newMediaLocaleFields` stamps `enContentVerified*` (title/overview as stored + `enContentVerifiedVersion`) on every light upsert whose English base was just fetched from the provider (`fetchEnBase`/`fetchEnBaseTvdb`) — the verifier would reach the identical conclusion, so this saves one provider call per row and stops live non-en search traffic from re-growing the suspect pool faster than the cron drains it (TMDB returns the ORIGINAL title in the en slot when no translation exists, so every searched foreign film was born suspect: ~8k/day vs 2k/day drain). The shared `EN_CONTENT_VERIFIER_VERSION` lives in `media-metadata/util/en-content-verifier.ts` (neutral module — the backfill service imports the metadata service, never the reverse). The `english_content_verify` cron processes 1000 rows/run (default `0 */6 * * *` for new installs; existing CronJob rows keep their DB schedule until edited in Scheduled Jobs).

## Metadata Health repair progress reporting

- Metadata Health separates raw inventory from actionable repair selectors. It reports typed authority (missing/invalid/outdated), active structural contamination, `LEGACY_UNMAPPED` episodes/shows/user-data rows, correct-kind TVDB fallback shows, wrong-kind aliases, pending character-vote items split across shows and movies, and fingerprinted TVDB-alias audit state. The character-ID repair performs correct-kind show `CAST_ONLY` refreshes and TMDB-safe movie cast-only enrichment; movie enrichment adds only verified TVDB role aliases/supplemental credits and never rewrites canonical movie metadata. Repairs (`anime-rehydrate`, `character-ids`, `tvdb-id-conflicts`, `wrong-kind-external-ids`, `english-base`, and others) update `repairProgress`; `GET /admin/metadata-health/repair-progress` exposes running jobs plus finished ones for 60s, and the page polls every 3s.
- The production health endpoint is snapshot-backed because its exact metrics scan the whole catalog. Fresh snapshots are returned immediately for 60 seconds; the last successful snapshot remains available for 24 hours. When stale, one distributed background refresh runs while the Admin page continues showing the old snapshot and polls for completion. A first-ever cold load returns a lightweight `._health.status = "refreshing"` response instead of holding an HTTP request open until the browser/proxy times out. This cache affects only Admin observability; repair selectors still query current rows when a repair actually runs.

## TMDB recommendations sync ("Similar shows/movies" rails)

- Storage: `media_items.recommendations` (JSON snapshot of card-shaped items: `{tmdbId, type, title, posterUrl (w342), year, rating}`, cap 20) + `recommendations_synced_at` (null = never synced). The snapshot rides the one-call hydration: `getShow/getMovie` append `recommendations` to `append_to_response` (shows: 12 season appends + 8 base appends = the 20 cap; seasons beyond the window still fall back to per-season fetches).
- **No-clobber rule:** TVDB supplies no recommendations, so `persistShow/persistMovie` write the snapshot + stamp via conditional spread (`...(data.recommendations ? {...} : {})`) — a TVDB refresh NEVER clobbers TMDB-synced recommendations.
- Read path: `getShowDetail/getMovieDetail` map the JSON snapshot into `ShowDetailDto/MovieDetailDto.recommendations` (`RecommendationDto`, parsed defensively — unknown shape → `[]`). Items carry the TMDB id, NOT the internal media id; the mobile rails (`show/[id].tsx`, `movie/[id].tsx`, above the Comments card) route taps through the numeric-TMDB-id path both routes already support. `MovieDetailDto.similar` is a dead field — `recommendations` supersedes it.
- Admin: Metadata Health `recommendationsMissing` stat (TMDB-linked rows with `recommendations_synced_at IS NULL`, minus 90-day-parked rows) + `POST /admin/repair-recommendations/run?count=` (`repairRecommendations`) — ONE light `/recommendations` call per row (no appends, no rehydration), popularity-first, stamps empty results too (provider has none → row leaves the stat), stops early on TMDB rate limits. Dead TMDB ids (real or negative-cached 404) are parked via `metadata_provenance.recsCheckedAt` and excluded from the stat + candidate selection for 90 days, instead of re-failing on every run.

## Provider-404 parking (all iterating repair/backfill jobs)

- Any cron/admin job that iterates media rows and calls a provider can hit rows whose external id is DEAD (deleted/merged at the source): both real `tmdb 404` and negative-cached `tmdb cached 404` surface as `ProviderError category 'not_found'` (`isNotFoundError`). Instead of re-failing every run, each job parks the row in `metadata_provenance` (atomic `|| jsonb_build_object` stamp via `stampRepairChecked`) and excludes it in its candidate SQL (and the matching Metadata Health stat) for 90 days — ISO strings compare correctly as text and cast cleanly to timestamptz. Keys: `recsCheckedAt` (recommendations), `charIdsCheckedAt` (character-ids), `countryCheckedAt` (movie countries), `bannerCheckedAt` (banner posters), `hydrateNotFoundAt` (generic `backfillBatch` stubs — parked ids are prefetched raw and excluded via `id: { notIn }` so they don't consume the batch limit), plus the pre-existing `ratingCheckedAt` (ratings). Non-404 errors are NOT parked — transient failures keep retrying; rate limits still stop the batch early. Summaries report a `parked` count alongside succeeded/failed.
- Cron: `recommendations_backfill` (`0 11 * * *`) → `repairRecommendations(500)`. Summary persists into `CronJobRun.result` like the other DB-managed jobs.
